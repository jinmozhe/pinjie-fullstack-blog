# 错误与失败模型

## 1. 原则

系统必须明确失败，禁止吞错、假成功、弱默认值和静默降级。错误响应需要让调用方稳定处理，让维护者通过关联 ID 定位，同时不泄露堆栈、SQL、凭据和敏感数据。

## 2. 错误分类

| HTTP 状态 | 使用场景 | 说明 |
| --- | --- | --- |
| `400` | 协议语义错误 | 请求结构有效，但通用协议语义不成立 |
| `401` | 未认证或凭据失效 | 必须包含适用的认证挑战信息 |
| `403` | 身份有效但无权执行 | 不泄露额外资源信息 |
| `404` | 资源不存在或按安全策略隐藏 | 避免通过错误差异枚举资源 |
| `409` | 业务状态或唯一性冲突 | 返回稳定业务错误码 |
| `412` | 版本或并发前置条件失败 | 用于 ETag、版本号等显式条件 |
| `422` | 输入结构或字段校验失败 | Pydantic 边界校验使用统一格式 |
| `429` | 请求速率受限 | 提供允许公开的重试信息 |
| `502` | 上游响应无效 | 当前服务无法解释上游结果 |
| `503` | 当前服务或关键依赖不可用 | 明确临时不可用，不伪造结果 |
| `504` | 上游调用超时 | 结果未知时禁止自动重复副作用 |
| `500` | 未处理内部错误 | 返回关联 ID，内部记录脱敏异常 |

## 3. 响应契约

后续实现的错误响应至少包含：

- 稳定的机器错误码。
- 面向调用方的中文安全消息。
- `request_id` 或 `trace_id`。
- 允许公开的字段级错误明细。

公开 API 的成功与失败响应顶层 `message` 必须使用中文。错误 `code`、HTTP 状态、参数名、字段名、字段路径和机器错误类型继续使用稳定的程序化标识；Pydantic 等框架生成的底层校验信息可以保留机器原文，但不得直接替代中文顶层消息。全局响应边界会将不含中文的意外消息收敛为中文通用消息。

响应不得包含 Python 异常类、堆栈、SQL、数据库地址、文件系统路径、Token、Cookie、密码、密钥或完整敏感载荷。

## 4. 分层职责

- Router 不捕获业务异常并转换为成功响应。
- Pydantic 负责输入结构、类型和局部字段校验。
- Service/Domain 负责需要当前状态或多字段语义的业务校验。
- Repository 让持久化错误向上分类，不吞掉异常。
- 全局异常处理器统一映射已知异常；未知异常返回 `500` 并记录关联 ID。

全局异常处理器是最后一道安全边界，不是业务降级入口。

## 5. 外部依赖失败

外部请求必须设置连接、读取和总超时。重试仅适用于可证明安全的瞬时失败，并设置次数、退避和总时间预算。

具有副作用的操作需要幂等键或结果确认。超时和连接中断可能代表结果未知，禁止立即重复提交并返回成功。结果未知必须进入可查询、对账或人工处理状态。

## 6. 允许的故障隔离

允许超时、有限重试、熔断、背压、只读模式和前端错误边界，但每项机制必须定义：

- 触发条件。
- 用户和调用方可见状态。
- 日志、指标和告警。
- 数据一致性影响。
- 自动或人工恢复条件。
- 对应测试。

没有完整定义的默认值、缓存旧值和替代数据不能作为故障隔离方案。

## 7. 禁止模式

```python
try:
    result = await dependency.call()
except Exception:
    return None
```

以上模式以及返回空集合、硬编码成功、默认管理员、弱密钥、默认生产地址、静默切换数据库或跳过验证均被禁止。确有可选能力时，产品契约必须明确“可选”和“不适用”状态，不能依靠异常触发隐藏路径。
