# ADR 0003: 本地开发环境架构决策

- 状态：已确认
- 日期：2026-08-10
- 决策者：大仙
- 操作手册：[local-dev-environment.md](../operations/local-dev-environment.md)

## 背景

本项目在 Windows 上开发，生产环境运行在安装了 1Panel 的 Linux 服务器。开发环境需要兼顾启动速度、调试体验、依赖可复现性和本地到生产的结构一致性。

后端已经采用 `pyproject.toml` 和 uv 管理依赖，前端采用 pnpm workspace 与 Turborepo。开发者电脑已有 PostgreSQL，并通过 Docker Desktop 提供适合容器化的基础服务。此前文档同时要求 `conda activate`、`uv sync` 和 `uv run`，会让 Conda 环境与 uv 默认项目环境 `.venv` 的职责发生重叠。

## 决策

本项目采用以下本地开发组合：

```text
Windows 本机进程
├── Backend：uv 管理标准 CPython 3.14、.venv、依赖和命令运行
├── Web：pnpm 启动 Next.js
├── Admin：pnpm 启动 Umi Max（Ant Design Pro v6）
└── PostgreSQL：使用本机安装的服务

Docker Desktop
└── Redis：通过根目录 compose.yml 启动
```

生产环境继续采用 1Panel 托管基础设施与应用容器：

```text
1Panel
├── OpenResty：反向代理和 SSL
├── 共享基础设施：PostgreSQL 与 Redis
└── 项目 Compose：backend、web、admin 和可选日志消费者
```

当前生产实现以根 `compose.prod.yml`、[ADR 0014](0014-共享PostgreSQL与Redis生产基础设施决策.md)和 [1Panel 单机生产运行手册](../operations/1panel-production-runbook.md)为准。PostgreSQL 和 Redis 由 1Panel 作为服务器级共享实例管理，项目应用通过外部 Docker 网络连接；每个项目使用独立 PostgreSQL 数据库与角色、Redis ACL 用户与 Key 前缀。

## 工具职责

| 工具 | 本项目职责 |
| --- | --- |
| uv | 安装或选择标准 CPython 3.14、创建 `.venv`、解析和锁定依赖、运行后端命令 |
| pnpm | 管理前端 workspace 依赖和脚本 |
| Turborepo | 编排多个前端 workspace 的开发、构建、检查任务 |
| 本机 PostgreSQL | 提供本地持久化数据库，采用单实例、多数据库、独立用户模式 |
| Docker Desktop | 只运行 Redis 等适合容器化的本地基础服务 |
| 1Panel | 管理生产网关、证书、数据库、Redis、应用容器、备份和日志 |

## Python 环境决策

共享开发流程采用纯 uv 模式：

```powershell
uv python install 3.14
uv python pin 3.14
uv sync
uv run <command>
```

项目文档和项目规则中不要求 `conda activate`。Anaconda 或 Miniconda 可以保留在个人电脑中服务其他项目，但不作为本仓库的前置依赖。

选择纯 uv 的原因：

- `uv sync --locked` 与已提交的 `uv.lock` 提供统一、可复现的项目依赖环境。
- `uv run` 直接在项目 `.venv` 中执行命令，无需手动激活环境。
- 避免 Conda 环境和 `.venv` 同时存在时出现解释器、依赖安装位置和命令来源歧义。
- CI、Docker 构建和本地开发可以围绕同一份 `pyproject.toml` 与 `uv.lock` 工作。

如果派生项目依赖 CUDA、复杂本地编译库或 Conda 专属包，应新增 ADR 说明例外，不能直接修改本母版默认流程。

## 本地与生产环境边界

| 维度 | 本地开发 | 生产环境 |
| --- | --- | --- |
| 操作系统 | Windows | Linux |
| 应用进程 | PowerShell 中直接运行 | Docker 容器 |
| Python | uv 管理的标准 CPython 3.14 与 `.venv` | 后端镜像内固定标准 CPython 3.14 补丁版本和镜像 digest |
| Node.js | 本机 Node.js 24+ 与 pnpm 11.17.x | Web/Admin 构建及运行镜像 |
| PostgreSQL | 本机服务，`localhost:5432` | 1Panel 托管实例 |
| Redis | Docker Desktop，`localhost:6379` | 1Panel 托管实例 |
| 网关与 TLS | 直接访问 localhost，不启用 TLS | 1Panel OpenResty 与自动证书 |
| 环境变量 | 各应用自己的本地 `.env` 文件 | 由 1Panel 或 Compose 注入 |
| 数据 | 仅本地测试数据 | 生产业务数据 |

本地与生产保持数据库类型、Redis 主版本、迁移文件和应用启动方式的语义一致。操作系统、网络地址、TLS、容器边界和凭据必须保持隔离。

Python 主次版本、补丁更新、CI 和容器固定方式以 [ADR 0009：Python 运行时基线决策](0009-Python运行时基线决策.md)为准。1Panel 宿主机 Python 不参与 Backend 运行时选择。

## 备选方案

### 方案 A：PostgreSQL 与 Redis 全部使用 Docker

优点是隔离完整、版本容易锁定。代价是与现有本机 PostgreSQL 和生产单实例多数据库模式存在额外差异，还需要管理独立端口与数据卷。本仓库当前 `compose.yml` 不提供 PostgreSQL 服务。

### 方案 B：Conda 环境结合 uv

uv 的 pip 接口可以发现已激活的 Conda 环境，uv 项目操作也可以通过显式环境配置改变目标环境。该组合会增加解释器发现和环境路径配置成本，不作为团队默认流程。

### 方案 C：完整 Dev Container

应用、数据库和工具链全部进入容器，环境隔离最强。当前 Monorepo 在 Windows 上更重视热重载、IDE 调试和多进程启动效率，因此暂不采用。

## 影响与代价

- 首次开发需要安装 uv、Node.js、pnpm、PostgreSQL 和 Docker Desktop。
- `.venv`、前端依赖和 Docker Redis 数据卷分别占用本地磁盘。
- 本机 PostgreSQL 需要开发者自行维护服务状态、数据库和用户。
- 生产问题仍需在 Linux 容器和 1Panel 环境中完成最终验证，本地通过不能替代生产冒烟。
- 切换 Python 小版本或依赖后需要重新执行 `uv sync` 并提交相应锁文件变化。

## 数据同步原则

- 本地测试数据不得直接覆盖生产数据。
- 数据库结构只通过 Alembic 迁移文件同步。
- 初始基础数据通过受控种子脚本生成。
- 确需迁移指定业务数据时，必须单独确认表范围、脱敏、导入顺序和回滚方案。
