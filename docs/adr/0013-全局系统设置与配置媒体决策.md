# ADR 0013：全局系统设置与配置媒体决策

## 状态

已接受，2026-08-29。

## 背景

站点名称、LOGO、标题、关键词、描述和公开注册开关需要由管理员在运行时修改。环境变量需要重启，JSON 文件缺少数据库事务、并发控制和稳定审计；每类设置一张单行表会制造大量低价值表；完全动态的键值与前端动态表单又会削弱强类型契约和字段级校验。

站点 LOGO 属于固定系统配置媒体。它没有文件资产的上传主体、场景、列表、去重和生命周期语义，写入统一 `assets` 表会产生错误关联。

## 决策

1. 使用单一 `system_settings` 表。一个源码声明的设置分组对应一行，值为 JSONB Object。
2. 第一阶段固定 `site` 与 `registration` 两个分组。Backend 使用固定 Pydantic Schema，Admin 使用固定 Ant Design 组件，不提供动态 `{group}/{key}` 公共接口或动态表单。
3. 管理写接口使用 PostgreSQL 行锁、正整数 `revision` 和 `412 SETTINGS_REVISION_MISMATCH` 防止覆盖其他管理员的修改，并记录最后修改者、时间和审计事件。
4. 公开注册只读取 `registration.enabled`。读取失败、缺行或数据无效时明确失败并保持关闭，不再保留 `REGISTRATION_MODE` 双轨。
5. Web 只通过 `GET /api/v1/system/site-profile` 获取完整、强类型、可公开的站点资料。消费者在本地选择字段，不增加 LOGO 单字段接口。
6. 配置媒体使用独立固定槽位。站点 LOGO 只允许静态 PNG、JPEG 或 WebP，服务端完整解码并固定保存为 `site/logo.{ext}`，不进入 `assets` 表。
7. 本地配置媒体使用同文件系统 staging、trash、原子替换和持久化操作清单。数据库提交失败时补偿文件；进程中断后按数据库 revision 与媒体元数据恢复。未知状态阻止就绪，禁止自动猜测。
8. 当前生产部署为单实例或共享文件系统边界。数据库与完整 `/app/storage` 文件卷必须使用同一备份窗口；多实例无共享文件系统时不得启用本地配置媒体写入。

## 结果

- 新配置域可以继续增加固定分组行、Schema、权限、接口和 Admin Tab，无需增加单行表。
- JSONB 内部字段由应用 Schema 约束，数据库只保证分组唯一、值为 Object 和 revision 为正数。
- Web 展示在站点资料不可用时回退内置 `Pinjie` 品牌；注册安全判断不使用该展示回退。
- LOGO URL 带 revision 查询参数。SiteProfile 不缓存，Web 同源媒体代理对有效 revision URL 返回长期 immutable 缓存。
- 配置媒体与文件资产需要分别维护，但领域语义、权限和恢复路径保持清楚。

## 未选择方案

- 环境变量：适合部署参数，不能支持运行时管理和事务审计。
- 本地 JSON：多进程一致性、权限、并发和恢复成本高。
- 每个配置域一张表：字段级数据库约束更强，但当前会产生大量单行表。
- 通用逐键接口和动态表单：扩展看似灵活，实际把类型、校验和安全边界推给运行时元数据。
- 复用文件资产：会把系统固定媒体错误建模为用户或管理员资产。
