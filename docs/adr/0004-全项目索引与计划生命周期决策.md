# ADR 0004: 全项目索引与计划生命周期决策

- 状态：已确认
- 日期：2026-08-12
- 决策者：大仙
- 适用范围：`pinjie-fullstack-base` 及其派生仓库

## 背景

本仓库是包含 Backend、Admin、Web、共享包、数据库和部署配置的通用全栈 Monorepo 母版，并将继续派生 CMS、电商、博客和企业站等业务项目。现有规则、文档和计划分别有自己的入口，但任务开始时缺少一个能够快速回答“当前项目是什么、三个应用分别在做什么、哪些计划有效、哪个文件是权威来源”的全项目导航。

FastNav 的集中索引方案验证了规则、文档、计划和目录状态统一导航的价值。本项目需要保留这种能力，同时避免在总索引中复制专项文档正文，避免按应用拆分计划，也要保证历史计划不会被 AI 自动整理或删除。

## 决策目标

1. 为人和 AI 提供稳定的全项目任务入口。
2. 明确整个 Monorepo 的当前阶段以及 Backend、Admin、Web 的当前开发目标。
3. 让所有计划原文、状态和结果长期可追溯。
4. 让派生仓库能够记录派生类型、母版基线和业务范围。
5. 避免总索引、文档索引和计划规范之间形成重复事实来源。

## 决策

### 全项目索引

使用 `PROJECT_INDEX.md` 作为全项目任务导航和当前事实入口。索引只包含：

1. 项目身份和母版基线。
2. 当前阶段。
3. 待确认、待实施和实施中的活动计划。
4. 规则、计划、文档、契约、Changelog 和安全治理的权威入口。

根索引只记录当前高频事实和必要入口，不复制历史计划、规则或文档正文。

索引固定放在仓库根目录，与 `AGENTS.md`、`CHANGELOG.md` 同层。`.agents/` 只保留 Antigravity 规则桥接文件，不保存需要在日常任务中持续写入的项目索引。该位置于 2026-08-29 经用户确认调整，避免 Codex 对受保护目录的写入边界反复阻塞索引同步。

### 全栈计划

`plans/` 属于整个全栈 Monorepo。计划以完整业务能力或工程目标为单位，同一功能涉及 Backend、Admin、Web、API Client 或 Database 时，使用同一份计划描述完整数据链路、实施顺序、契约同步和联合验证。

计划文件直接放在 `plans/` 下，不创建 `active/`、`archive/`、按年份或按应用划分的目录。计划使用“待确认、待实施、实施中、已结束”四种状态；已结束计划另填“已完成、已取消、已替代”结果。

### 计划永久登记

使用 `plans/INDEX.md` 作为全部实施计划的唯一永久登记入口。每条登记只保存计划路径、状态、结果、影响范围和一句话用途，不复制计划正文。

新建计划时同步加入 `plans/INDEX.md`。计划状态或结果变化时同步计划原文和永久登记；只有活动性发生变化时才同步根目录 `PROJECT_INDEX.md`。`plans/README.md` 和 `plans/INDEX.md` 是治理文件，不属于实施计划，不进入永久登记表。

### 计划永久保护

已经存在的计划文档属于永久项目资产。AI 不得删除、移动、重命名或替换计划文档，只能在原文件中更新内容、状态、结果和验证事实。每份实施计划必须在 `plans/INDEX.md` 中保留唯一登记，计划结束后也不得移除登记。

计划文件的删除、移动和重命名只能由用户人工处理。用户人工处理后，AI 可以根据新的文件事实同步索引。

### 索引职责

| 文件 | 职责 |
| --- | --- |
| `AGENTS.md` | 长期执行规则和读取顺序 |
| `PROJECT_INDEX.md` | 项目身份、当前阶段、活动计划和权威入口 |
| `plans/INDEX.md` | 全部实施计划的唯一永久登记 |
| `plans/README.md` | 计划创建条件、格式、状态、完成和保护规则 |
| `plans/*.md` | 全栈实施计划正文和实施结果 |
| `docs/README.md` | `docs/` 文档的完整专项索引 |
| `docs/adr/*.md` | 长期技术决策及其理由 |
| `CHANGELOG.md` | 已交付能力和版本变化 |

### 2026-08-29 职责拆分补充

本 ADR 背景和原始目标中“当前状态”“三个应用当前开发目标”描述的是建立统一导航入口时需要解决的问题。根索引完成职责拆分后，这些信息按以下边界解释：

1. `PROJECT_INDEX.md` 只维护项目身份、当前阶段、活动计划和权威入口，不维护逐应用的完整实现清单。
2. 某个应用当前正在处理的目标通过根索引中的活动计划定位，活动计划原文保存范围、顺序和验证。
3. 某项能力是否已经实现，以实际源码、配置、迁移、生成契约和对应架构文档为证据；根索引中的阶段摘要不能单独作为实现证据。
4. `CHANGELOG.md` 继续记录已经交付的变化，`plans/INDEX.md` 继续保存全部计划的永久登记。

## 与 ADR 0002 的关系

ADR 0002 继续生效。`PROJECT_INDEX.md` 是项目导航和当前事实索引，不是规则正文，也不替代根或应用级 `AGENTS.md`。`.agents/rules/` 继续只负责 Antigravity 的规则加载桥接，本决策不引入 `.agents/AGENTS.md`。

## 派生项目规则

派生仓库继承总索引和计划治理机制，并在“项目身份”中更新：

1. 项目角色。
2. 派生类型。
3. 母版标签或提交 SHA。
4. 当前阶段。
5. 业务范围。

母版中已经存在的计划原文和 `plans/INDEX.md` 登记继续保留。派生业务通过新的全栈计划和业务文档扩展，不修改母版历史计划来伪造派生项目历史。

## 代价与风险

1. 每次计划状态或结果变化需要同步计划原文和 `plans/INDEX.md`；只有活动计划变化时才同步根索引。
2. 计划数量长期增长时目录会变大，但路径稳定和历史完整优先于自动归档的便利。
3. `plans/INDEX.md` 会随计划增长，但低频历史登记不会扩大每次任务必须读取的根索引。
4. 当前事实若未及时同步会失真，因此任务交付前必须检查根索引、计划永久登记、计划原文、文档和 Changelog。

## 验证要求

1. 根规则能够稳定路由到根索引、计划规范和计划永久登记。
2. 根索引能够直接展示项目身份、当前阶段、活动计划和权威入口。
3. `plans/` 下每份实施计划均在 `plans/INDEX.md` 中唯一登记。
4. 计划保护规则同时存在于根规则和计划规范。
5. 派生仓库可以通过项目身份字段记录母版基线和业务范围。
6. 根索引不复制 `docs/README.md` 的完整文档清单或 `plans/INDEX.md` 的历史计划登记。
