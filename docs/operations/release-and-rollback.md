# 博客发布与回滚

## 当前状态

博客尚未配置域名、镜像仓库、CNB 目标、服务器或生产数据。GitHub 轻量 CI 保留；Publish Images、Deploy Production、Validate Candidate Images 和 CNB 镜像入口第一步均明确失败，CNB 不导入任何外部 Secrets 文件。

现有容器、镜像检查和发布工具保留供后续接入。根 .env.example 的镜像名和零 digest 仅为公开模板，不能用于实际部署。其余发布手册中的历史环境和验证数字只作为继承参考。

## 启用条件

1. 在博客首版全栈计划中明确博客自己的域名、镜像仓库、部署目录、数据库角色、Redis 隔离、媒体卷、备份目标及恢复方式。
2. 更新博客工作流、CNB 与脚本中的目标校验、镜像名称和授权环境；禁止复用母版 Secrets、镜像或生产目录。
3. 为博客仓库单独配置最小权限凭据，真实值不得入库或写入日志。
4. 完成静态检查和用户明确授权的测试、构建、数据库及恢复验收，记录实际结果。
5. 在同一经评审修改中移除阻断步骤并补齐独立目标检查；不能仅删除 exit 1 后直接触发继承链路。
6. 分别取得发布、部署授权后才运行相应入口。

## 交付顺序

源码修改、提交推送、质量检查、镜像发布、生产部署和回滚分别授权。默认 CI 只执行轻量检查及线上 Security；重型验证需明确授权，不能通过调用其他 Workflow 间接运行。

发布记录保存博客完整 Commit SHA、实际 Workflow Run、镜像 digest、扫描与来源证据。生产只使用固定 digest，不使用 latest 或分支标签。

## 部署与恢复

生产 Compose 使用项目名 pinjie-fullstack-blog 和独立媒体卷。数据库可以位于共享 PostgreSQL 实例，但必须使用博客自己的数据库和最小权限账号；Redis 必须有独立命名空间与权限边界。

部署前保存上一组镜像 digest、数据库 revision、数据库及媒体备份。迁移遵守 Alembic 链和目标确认，不因应用启动自动执行。

故障时先记录影响范围、当前版本和恢复点。镜像回退不能替代数据库恢复，也不能恢复已删除图片。数据库与媒体必须按同一可核对时间点恢复并验证记录、引用和读取链路。回滚与恢复生产数据继续单独授权。
